02 · PROBLEM

Kenapa HTTP Aja Nggak Cukup?

❌ HTTP Polling
  • Client harus tanya server tiap detik
  • Boros bandwidth & battery device
  • Latency tinggi, bukan real-time
  • Stateless — server nggak tau siapa online
  • Overhead header gede tiap request
✅ MQTT Pub/Sub
  • Device push data saat ada perubahan
  • Header cuma 2 byte — super hemat
  • Real-time persistent connection
  • Broker kelola semua koneksi
  • Cocok buat device kecil & jaringan tipis

05 · TOPIC

Topic — Alamat Pesan MQTT

Topic itu kayak channel YouTube — publisher upload ke channel, subscriber follow channel. Format hierarki pakai /.

rumah/ruangtamu/lampuLampu di ruang tamu
pabrik/lini-1/mesin/suhuSuhu mesin di lini produksi 1
kebun/+/kelembapan+ = wildcard 1 level (semua kebun)
gedung/## = wildcard multi level (semua di bawah gedung)
💡 Pro Tips
  • Pakai huruf kecil, hindari spasi & karakter spesial
  • Mulai dari general → spesifik (kayak path file)
  • Jangan pakai / di awal — bikin "empty level"
06 · QoS

Quality of Service — Jaminan Pengiriman

QoS 0
At Most Once
Fire and forget. Pesan dikirim sekali, nggak ada konfirmasi. Mungkin hilang.
Use case: data sensor yang sering update (suhu tiap detik)
QoS 1
At Least Once
Ada konfirmasi (PUBACK). Pesan dijamin sampai, tapi bisa duplikat.
Use case: notifikasi penting yang boleh muncul 2x
QoS 2
Exactly Once
4-way handshake. Pesan dijamin sampai tepat 1 kali. Paling lambat.
Use case: transaksi pembayaran, command kritis
07 · FITUR

Fitur MQTT Yang Wajib Tau

📌

Retained Message

Broker simpan pesan terakhir di topic. Subscriber baru langsung dapat nilai terbaru tanpa nunggu publish baru.

⚰️

Last Will (LWT)

Pesan otomatis dipublish kalau client disconnect mendadak. Buat deteksi device offline.

💓

Keep Alive

Client kirim PINGREQ tiap N detik. Broker tau client masih hidup atau udah putus.

🧹

Clean Session

Atur apakah broker simpan subscription & pesan saat client offline, atau reset tiap reconnect.

09 · KODE

Publisher di Node.js

const mqtt = require('mqtt');
const client = mqtt.connect('mqtt://broker.hivemq.com', {
  clientId: 'sensor-01',
  username: 'user',
  password: 'pass',
  clean: true,
  keepalive: 60
});

client.on('connect', () => {
  // Publish suhu tiap 5 detik
  setInterval(() => {
    const suhu = (25 + Math.random() * 5).toFixed(1);
    client.publish('rumah/ruangtamu/suhu', suhu, { qos: 1, retain: true });
    console.log(`📤 Suhu: ${suhu}°C`);
  }, 5000);
});
10 · KODE

Subscriber di Browser (WebSocket)

// Pakai MQTT.js via CDN, connect lewat WebSocket
const client = mqtt.connect('wss://broker.hivemq.com:8884/mqtt');

client.on('connect', () => {
  console.log('✅ Connected');
  client.subscribe('rumah/+/suhu', { qos: 1 });
});

client.on('message', (topic, payload) => {
  const suhu = payload.toString();
  const ruangan = topic.split('/')[1];
  document.getElementById(ruangan).textContent = `${suhu}°C`;
});

client.on('error', (err) => console.error(err));
11 · ALUR

Alur End-to-End Sistem IoT

  1. Sensor / device baca data fisik (suhu, kelembapan, tombol)
  2. Microcontroller (ESP32/Arduino) format jadi pesan MQTT
  3. Publish ke broker via WiFi/Ethernet/4G
  4. Broker route pesan ke semua subscriber yang match topic
  5. Backend Node.js simpan ke database + logic bisnis
  6. Frontend web subscribe via WebSocket, render real-time
  7. User kirim command balik (nyalain lampu) → publish topic kontrol
  8. Device subscribe topic kontrol, eksekusi aksi fisik
12 · SECURITY

Keamanan MQTT

🔐

TLS / SSL

Pakai mqtts:// (port 8883) atau wss:// (port 8884). Enkripsi end-to-end antara client dan broker.

🆔

Username & Password

Auth dasar via CONNECT packet. Wajib dikombinasi dengan TLS karena password dikirim plain.

📜

Client Certificate

Auth via X.509 certificate. Lebih aman buat device produksi, tiap device punya cert unik.

🚫

ACL (Access Control)

Atur siapa boleh publish/subscribe ke topic mana. Cegah device A baca data device B.

14 · PITFALL

Kesalahan yang Sering Terjadi

  • ❌ Pakai broker public buat data sensitif — broker.hivemq.com itu publik, semua orang bisa subscribe.
  • ❌ Topic terlalu generik — data bukan topic, rumah/ruangtamu/suhu baru topic.
  • ❌ Lupa setting QoS — default 0, command kritis bisa hilang tanpa kamu sadar.
  • ❌ Client ID duplikat — broker akan disconnect yang lama, device mantul-mantul.
  • ❌ Nggak handle reconnect — koneksi IoT pasti putus, harus auto-reconnect.
  • ❌ Publish JSON gede-gede — MQTT didesain buat payload kecil, kalau perlu file pakai HTTP.
